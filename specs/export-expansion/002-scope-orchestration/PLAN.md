## Goal & user value

"Export this handbook" almost never means "this one page" — documentation lives as a page tree. Today the ts engine explicitly rejects `--include-children` (`apps/cli/src/commands/export.ts:759-761`, cliNote "not supported by the ts engine yet"). This spec delivers:

- **One shippable document from a page tree or a whole space** — chapters follow the page hierarchy (page depth = chapter level), with a working table of contents and working cross-page links. Space export covers compliance/offboarding/archive JTBDs.
- **Curated exports via labels** — `internal` pages pruned out, or only `handbook` pages in; the standard migration pattern from established exporter workflows.
- **A headless story (A5)**: the same `fetchExportTree` → `composeChapters` → engine pipeline is the library API; the CLI with `--json` reports and deterministic exit codes is the "API" for CI pipelines. No hosted job polling, no data egress to third parties.

All of it lands once in `@atlcli/confluence` and is consumed identically by CLI, extension, further hosts.

## Architecture (isomorphic)

One scope-agnostic orchestration layer in `@atlcli/confluence` (fetch + composition on `ExportBlock[]` level). The engines stay single-document serializers — they never see that the document came from multiple pages.

```
ExportScope ──▶ fetchExportTree(TreeSource, scope, {labels, maxPages, signal, onProgress})
                     │  ordered walk, label pruning, cycle/depth guards, concurrency pool
                     ▼
               ExportNode[] ──▶ composeChapters(nodes, opts)
                                         │  heading shift, pageBreak per chapter,
                                         │  anchor namespacing, link rewrite
                                         ▼
                                   { blocks: ExportBlock[], notes } ──▶ @atlcli/docx runExport
                                                                    └─▶ @atlcli/pdf runPdfExport
```

- **New modules** (all isomorphic, exported from `packages/confluence/src/index.ts` **and** `index.browser.ts`, zero Node-only imports):
  - `packages/confluence/src/export-scope.ts` — serializable `ExportScope` (`page` | `tree` | `space`) and `LabelFilter` types. Serializable on purpose: CLI flags and extension URL/panel state map to the same object.
  - `packages/confluence/src/tree-fetch.ts` — `TreeSource` **port** (not `ConfluenceClient` directly) + `fetchExportTree`. The port exists so further hosts (e.g. an extension session-fetch adapter, folder 010) reuse the logic unchanged — same pattern as `PdfAssetResolver` (`packages/pdf/src/types.ts:26`). The Node adapter maps 1:1 onto the existing client, dispatching per node type (see Traversal order below) rather than a single flat `getChildren`.
  - `packages/confluence/src/compose-document.ts` — `composeChapters` chapter merge, consumed by DOCX **and** PDF paths.
- **Traversal order**: pre-order depth-first (document order). A tree node is **typed** (`page` | `folder`) because the two content types live behind different endpoints with no shared position field: `ConfluenceClient.getChildrenWithPosition` (`client.ts:911`, real UI position, cursor-paginated, **pages only** — a folder parent 404s here) vs. `getFolderChildren` (`client.ts:2521`, takes a **folder id**, no position field) — not the CQL-based `getChildren` (`client.ts:998`), which has no position guarantee either. These two cannot be "merged" directly (different parent-id semantics); the adapter must first discover child *types* via `getPageDirectChildren` (`client.ts:1007`, `GET /api/v2/pages/{id}/direct-children`, already returns mixed page/folder/whiteboard children of a **page** parent in one call, but without position), then dispatch per discovered type: page children re-fetch position via `getChildrenWithPosition`, folder children recurse via `getFolderChildren` for *their* children (folders have no position field — sorted by title as a stable fallback, `ExportNote { code: "folder-position-unknown" }`). Folder nodes never trigger `getPageDetails`/body fetch — folder = structure without body → chapter heading without content. (UMSETZUNGSPLAN's "BFS" shorthand is superseded by BASELINE-DESIGN's pre-order requirement; pre-order is what yields book order.)
- **Pagination completeness**: `getChildrenWithPosition`, `getPageDirectChildren`, and `getFolderChildren` share one latent bug — each ends its cursor loop on `if (!nextLink || results.length < limit) break;` (`client.ts:956`, `:1054`, `:2561`), i.e. a page that returns fewer than `limit` results **while still carrying a valid `_links.next`** is treated as the last page and the remaining pages are silently dropped. Confluence Cloud can return short pages with a live `next` link (permission-filtered items, internal page-size adjustments). `fetchExportTree`'s completeness guarantee (never a silently truncated document — see Safety rails) depends on fixing this at the client: only the *absence* of a next link/cursor ends pagination; a repeated link/cursor is a `pagination-loop` fatal, not a silent stop. This is shared client infra (all three callers), fixed once, benefiting every existing consumer too.
- **Space = tree** whose root is the space homepage (`scope.kind: "space"` resolves the homepage id, then delegates to the tree walk, root included). No separate codepath. Homepage lookup uses the existing single-round-trip `GET /space/{spaceKey}?expand=homepage.id` pattern (see `getSpaceHomepageStorage`, `client.ts:2793-2799`, which already expands `homepage.body.storage` in one call) — **not** `getSpaceFolders`' CQL-search-then-N-sequential-`getPage()` homepage detection (`client.ts:2575-2598`), which costs up to 51 requests just to find the root.
- **Safety rails**: `visited: Set<string>` cycle guard keyed on a composite `"kind:id"` string, not id alone (a page and a folder can share the same underlying content id in theory; keying on id alone would under-detect), note `tree-cycle` + skip; `maxDepth`; `maxPages` (default 500, pages only) **and** `maxFolders` (default 200) with a hard, early, actionable error — never a silent hang or a degraded mega-document (folders carry no body but are unbounded structure otherwise: a pathological folder tree must not bypass the page cap's intent). A discovered child whose kind is neither `page` nor `folder` (whiteboard, database, embed — anything `getPageDirectChildren` reports beyond the two traversable kinds) is never traversed or cast into a page/folder shape; it is reported as `ExportNote { code: "unsupported-child-type", kind }` and skipped, node + descendants (skipping without descending is the same privacy/cost posture as label pruning). **Completeness policy is a closed contract, not a per-caller choice re-litigated later**: `TreeFetchOptions.completenessMode: "strict" | "partial"`, default `strict`. In `strict` mode any of the following aborts the export with a typed, non-overlapping error code: `page-unreadable` (401/403 on body fetch), `subtree-unreadable` (401/403 during discovery — the affected page ids/titles are collected before abort, not just the first hit), `page-ambiguous-404` (a 404 that `sync-db/types.ts:10-17`'s existing model already treats as delete-vs-permission-ambiguous — Confluence returns the same status for "deleted" and "you can't see this"), and `page-version-changed` (the page's `version` at body fetch differs from `observedVersion` captured during the ordering walk — see the version-snapshot task below; long tree walks are not a point-in-time snapshot without this check). `partial` is an explicit opt-in (CLI: `--completeness partial`, default `strict`) that downgrades every one of those four codes to a structured `ExportNote` (same code names) carrying the affected page id(s)/title(s), sets `FetchExportTreeResult.complete: false`, and renders a visible placeholder chapter instead of a silent omission. Both `TreeFetchOptions.completenessMode` and `FetchExportTreeResult.complete` are the two ends of this contract — a caller that never sets the option always gets `complete: true` or an abort, never a result that quietly omitted content. This closes the "unreadable pages" and "excluded/unreadable root" questions that earlier drafts of this plan left open in two places at once (see Tasks and Risks below — the open-question entries there are now resolved, not restated): a document that *looks* complete but silently isn't is worse than a hard failure, especially for the compliance/archive JTBD (A2). Memory: blocks are small, assets are big — both engines share one asset-budget contract (`AssetBudget`, see Engine integration) so PDF's existing 50 MiB total cap and DOCX's new equivalent behave the same way: deduplicate by content hash before the cap check, fail early with the offender list and suggestions (`--max-depth`, `--no-images`), and treat a budget breach as a fatal scope-level error in both engines — never a per-image warning that lets an incomplete document "succeed" (today's DOCX behavior, see Engine integration).
- **Root & filter semantics (closed, not left to the filter task alone)**: the export root behaves differently under label filters than under `includeRoot`, and the two were previously in tension (a filter task that hard-errors on "excluded root" vs. an E2E fixture that left the root unlabeled and still expected success). Resolved: **label filters never remove the export root as an error condition** — a root that fails an `include` list or matches an `exclude` list is kept as *structure* (title/chapter heading, no body-level exclusion note beyond a single `ExportNote { code: "root-filter-bypassed" }`), because a tree/space export with zero top-level structure reads as broken, not curated. Only `scope.kind: "tree"` with `includeRoot: false` removes the root *by explicit request*, never as a side effect of a label. Downstream of any `page-only` exclude or non-matching `include`, a removed node's children are **reparented** to the nearest surviving ancestor (root if nothing else survives) and carry an explicit `effectiveDepth` (distinct from their original tree `depth`) that `composeChapters` uses for chapter-level assignment instead of raw `depth` — this is what prevents an H3 chapter appearing with no H1/H2 ancestor once an intermediate page or folder is filtered out. If reparenting leaves more than one node at `effectiveDepth 0` (e.g. `includeRoot: false` with several surviving children), each becomes its own level-1 chapter — multiple independent top-level chapters, not an error.
- **Progress/abort**: child listing is sequential (ordering!), body fetch + `storageToBlocks` run in a concurrency pool (default 4). `onProgress` drives the CLI spinner; the PDF engine's `onPhase` (`run-export.ts:30`) stays the phase-level channel and gains per-asset detail. Extension progress UI consumes the same callbacks — port note only, wiring in folder 010. **Abort is real, not best-effort**: today `ConfluenceClient.request`/`requestV2` (`client.ts:247`, `:376`) accept no `signal` and never pass one to `fetch`, and the 429/5xx retry backoff (`client.ts:171` `sleep()`, a bare `setTimeout`) cannot be interrupted — so a `throwIfAborted` check between page fetches (the PDF pattern at `run-export.ts:59`) only stops *new* work, not an in-flight request or a multi-second retry sleep (worst case ~7s at today's `maxRetries=3`/`baseDelayMs=1000`). This spec threads `signal` into both HTTP helpers and makes the retry sleep abortable, so Ctrl-C during discovery, backoff, or body fetch actually stops network I/O, not just orchestration. **`requestBinary()` (`client.ts:1678`) is a separate method that does not call `request`/`requestV2`** and is the path attachment/asset downloads use (`client.ts:1566`) — folder 008's PDF asset-fetch cancellation task depends on this being covered too (`008-pdf-cli/PLAN.md`, cancellation-contract task); thread `signal` into `requestBinary` as well in this same task, not just `request`/`requestV2`, or the "Abort is real" guarantee above does not hold for the asset-fetch phase of a tree/space export. DOCX's `RunExportInput` (`packages/docx/src/env.ts:79`) has no `signal` field at all today (PDF's `RunPdfExportInput.signal`, `run-export.ts:29`, is the precedent) — add it. A `signal` on `RunExportInput` alone does not make abort real end-to-end: today's `AssetFetcher.fetch(ref)` and `OutputSink.emit(name, bytes)` (`packages/docx/src/env.ts:35,39`) take no context at all, `runExport` (`env.ts:90-103`) never checks the signal between the template load / export / emit phases, and the CLI's `tokenAssetFetcher` (`apps/cli/src/commands/export-internals.ts:113-145`) calls the global `fetch(ref.url)` for external images and `client.downloadAttachment(...)` for attachments with no signal either — so Ctrl-C during a large tree/space export's asset-heavy phase would still let in-flight image downloads and the final file write run to completion. Extend `AssetFetcher.fetch` and `OutputSink.emit` to accept an optional second `context: { signal?: AbortSignal }` argument (mirrors the `TreeSource` port context), thread it from `RunExportInput.signal` through `runExport`, and pass it into `fetch(ref.url, { signal })` / attachment downloads in `tokenAssetFetcher`; add a `throwIfAborted` check in `runExport` before the emit phase. Output must also be atomic: DOCX's `fileOutputSink` (`packages/docx/src/node-adapters.ts:29-38`) writes the target path directly today, so an abort or crash mid-write can leave a corrupt file at the destination; write to a sibling temp file and rename only on success (PDF's `--format pdf` sink in folder 008 already commits to this exact pattern, including the exclusive-create/rename/cleanup details — DOCX's sink adopts the same one here, as its own task, see Engine integration).
- **Pool ordering & drain**: concurrency (parallel body fetch) and pre-order (deterministic output) are both required, so the pool must deliver results *in discovery order regardless of completion order* — the same in-order-delivery limiter `packages/pdf/src/prepare.ts:78-136` already implements for asset fetching (index-tagged jobs, a `finished` map, and a `flush` that only resolves consumers once every lower index has settled) is reused (moved to a small shared internal helper, imported by both `tree-fetch.ts` and `prepare.ts` — one implementation, not two). Body-fetch results and their `ExportNote`s are written into pre-assigned pre-order slots (assigned during the sequential listing pass, before any body fetch starts), never appended in completion order. All jobs the pool has already started are drained with `Promise.allSettled` (never a bare `Promise.all`, which would leave later-started jobs' rejections unhandled once the first one wins the race) — if multiple jobs reject, the reported primary error is deterministically the one at the *earliest pre-order slot*, not whichever settled first, so the same input tree always reports the same primary failure across runs.
- **Engines untouched in shape**: the composed document always starts at heading level 1, so the existing promotion offsets (`computeHeadingOffset`, `packages/docx/src/serialize.ts:243`; `min - 1` in `packages/pdf/src/serialize.ts:838` via `writer.headingOffset`, used at `serialize.ts:654`) compute 0 automatically — no engine rebuild, only the shared helper is lifted and small anchor/bookmark additions land. `computeHeadingOffset` only subtracts the page's minimum level; it does not repair non-monotonic sequences within a page (e.g. H2→H1→H2) — that is source content the export faithfully reproduces, not a defect this spec introduces, so no normalization pass is added here (flagged as an open question below, not a task).
